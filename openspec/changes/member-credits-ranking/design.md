## Context

本工具的 Included credits 卡片以 org 為單位顯示本月消耗與內含額度分母（分母來自環境變數 INCLUDED_CREDITS，經 /api/config 回傳）。成員別用量目前只存在於 member-usage-modal：點擊 user-scope 預算卡片後，前端以 /api/premium-usage 帶 user 參數、對本月 1 日至今逐日並行查詢，再依 model 聚合成折線圖，結果以「成員名 + 抓取日期」為 key 存入 session 記憶體快取。

2026-09-01 促銷期結束後，每席內含額度由 3000 降回 1900，本 org（Copilot Business、4 席）分母由 12000 變為 7600。池子縮小 37%，但既有介面無法橫向比較成員消耗，且 GitHub 的 user-scope budget 只在超額後才計數（8 月實測：593.873 credits 全額折抵、netAmount 為 0），無法作為早期警示。

實測確認的資料源事實：
- GET /orgs/{org}/copilot/billing/seats 回傳 total_seats 與 seats 陣列，每筆含 assignee.login，本 org 為 4 人
- premium_request 用量端點的 org 層級回應僅依 model 拆分，不含使用者欄位；要取得成員別資料必須帶 user 參數逐人查詢
- 該端點的數量欄位為 grossQuantity（非 quantity），單價 0.01 美元/credit

## Goals / Non-Goals

**Goals:**

- 讓使用者在單一畫面看出本月哪些成員消耗最多 credits，以及各自佔內含額度的比例
- 成員名單涵蓋所有已指派席次者，不因該成員未設定 budget 而遺漏
- 取數請求數維持在合理範圍，不因新增卡片而使頁面載入明顯變慢
- 排行的合計數與 Included credits 卡片的分子可對照，不得出現無法解釋的落差

**Non-Goals:**

- 不改動 member-usage-modal 的觸發方式、圖表內容與既有快取行為
- 不改動 Included credits 卡片的分子分母定義與呈現
- 不新增 npm 相依套件、不引入打包工具
- 不做跨月比較、趨勢圖或匯出功能
- 不代為修改或建議 GitHub budget 金額

## Decisions

### 席次名單取自 Copilot 席次端點而非既有預算資料

新增後端唯讀代理路由取得 GitHub 的 Copilot 席次名單，作為排行卡片的成員來源。

否決的替代方案是沿用前端已有的 user-scope 預算清單推導成員名單：該清單只涵蓋「有設定 budget 的人」，一名持有席次但未設 budget 的成員會完全不出現在排行中——而這正是本卡片要偵測的對象（默默吃掉共享池且無任何預算警示的人）。目前四名席次持有者恰好都設有 budget，兩種來源結果相同，但正確性差異在新增成員時就會浮現。

代理路由與既有路由採相同形式：後端帶 token 呼叫 GitHub、原樣轉發狀態碼與 JSON body，前端不接觸 token。

### 逐人取數只查詢有用量的日期

排行需要每位成員的本月消耗總量。直觀作法是對每位成員都執行「1 日至今逐日查詢」，成本為 成員數 × 當月已過天數（月底時 4 人 × 31 天 = 124 次請求）。

改採兩段式：先取得 org 層級的本月逐日資料（此資料為既有每日用量圖表所需，已存在 session 快取中，取用不產生新請求），篩出「該日有用量項目」的日期集合，再僅對這些日期逐人查詢。依據是一項可證的不變性——org 層級的用量為全體成員加總，某日 org 層級無任何項目時，該日任一成員必然也無項目。以 8 月為例只有 4 天有用量，成本由 124 次降為 16 次。

安全性處理：org 層級某日查詢失敗時無法判定該日是否有用量，該日一律納入逐人查詢範圍（保守側），避免因單日失敗而漏算成員消耗。

### 排行卡片的分子分母與未歸戶差額

每位成員的消耗值為其所有查詢結果項目的 grossQuantity 加總，四捨五入至整數並加千分位；百分比與比例 bar 的分母取 /api/config 回傳的 includedCredits，沿用 Included credits 卡片既有的 bar 著色門檻。includedCredits 為 null 時只顯示消耗值，不顯示百分比與 bar。

列表依消耗值由高到低排序，消耗為 0 的成員仍列出並排在最後，使「這個月誰完全沒用」同樣一眼可見。

若全體成員消耗加總小於 org 層級同期加總，差額以「未歸戶」列補在最後並標註說明。此設計避免排行看似完整卻實際遺漏部分消耗（例如無法歸屬到特定使用者的用量），使排行合計恆等於 org 合計、可與 Included credits 卡片對照。

### 排行取數使用獨立快取鍵，不污染成員 modal 快取

排行只查詢部分日期，其結果不足以支撐 member-usage-modal 所需的完整每日折線圖。若寫入既有以成員名為鍵的快取，後續開啟該成員 modal 會取得殘缺資料並畫出錯誤圖表。

因此排行的查詢結果存入獨立命名空間的快取鍵，與既有成員快取並存；沿用既有的「抓取日期不同即視為過期」規則。代價是使用者若先看排行再開 modal，該成員的資料會再查一次；此代價可接受，且完全避免了跨用途的資料污染風險。

### 失敗降級在卡片內部完成

任一成員的任一日查詢失敗時，該日以警告訊息記錄於瀏覽器主控台並以缺值處理，不中斷其他成員的計算；卡片在標題區顯示「部分資料讀取失敗」提示，使數字不會被誤讀為完整值。席次名單取得失敗時，卡片顯示錯誤訊息取代排行內容，不影響頁面其他卡片。此行為與既有卡片的降級慣例一致。

## Implementation Contract

**Behavior：**

頁面載入後，除既有卡片外多出一張「本月成員 credits 消耗排行」卡片。卡片列出所有 Copilot 席次持有者，依本月消耗 credits 由高到低排序。每列顯示成員名稱、消耗 credits（整數、千分位）、佔內含額度百分比與比例 bar。內含額度未設定時，該列只顯示消耗值。成員消耗加總小於 org 合計時，末列額外顯示未歸戶差額。

**Interface / 資料形狀：**

- 新增後端路由：GET /api/copilot-seats，無查詢參數，原樣轉發 GitHub 回應（含 total_seats 與 seats 陣列，成員登入名位於每筆的 assignee.login）
- 沿用既有路由：GET /api/premium-usage，查詢參數為 year、month、day、user；回應項目的消耗數量欄位為 grossQuantity
- 沿用既有路由：GET /api/config 取得 includedCredits
- 前端新增一個取得席次名單的函式、一個依指定日期集合逐人取數的函式，以及一個繪製排行卡片的函式；日期集合由既有的 org 逐日資料推導

**Failure modes：**

- 席次名單請求失敗：卡片內顯示錯誤訊息，其他卡片不受影響
- 個別成員的個別日期請求失敗：主控台記錄警告，該日視為缺值，卡片標題區顯示部分失敗提示
- includedCredits 為 null：不顯示百分比與 bar，僅顯示消耗值（與 Included credits 卡片一致）
- 全體成員消耗皆為 0：仍列出所有成員，顯示 0

**Acceptance criteria：**

- 以 npm run dev 啟動後開啟頁面，排行卡片出現且列出四名席次持有者
- 排行各列消耗值加總（含未歸戶列）等於 Included credits 卡片顯示的本月消耗值
- 瀏覽器開發者工具的網路面板顯示：對 /api/premium-usage 帶 user 參數的請求數等於「席次人數 × 有用量日數」，而非「席次人數 × 當月已過天數」
- 先開啟排行卡片、再點擊任一成員卡片開啟 modal，modal 的每日折線圖仍涵蓋 1 日至今完整區間（證明快取未被污染）
- 以本月無任何用量的情境（例如新週期首日）開啟頁面，卡片列出全部成員且值為 0，不出現錯誤

**Scope boundaries：**

- In scope：src/server.ts 新增席次代理路由；public/index.html 新增排行卡片的取數、聚合與繪製
- Out of scope：member-usage-modal 的任何行為、Included credits 卡片、每日用量圖表、預算列表與 PATCH 修改流程、.env.example、後端既有路由的參數驗證

## Risks / Trade-offs

- [org 層級單日資料失敗時，保守納入全部可疑日期會使請求數退回接近最壞情況] → 僅在失敗日發生時退化，且失敗已於主控台記錄；正確性優先於請求數
- [排行與 modal 各自查詢造成同一成員資料被查兩次] → 刻意接受，換取兩者快取互不污染；兩者皆有 session 快取，重複僅發生一次
- [未歸戶差額若長期存在可能令人困惑] → 該列附說明文字，指出其為無法歸屬到特定使用者的消耗，而非計算錯誤
- [席次人數增加時請求數線性成長] → 本 org 為 4 席，且已用有用量日篩選壓低基數；席次規模顯著成長時再評估改用批次或伺服器端聚合
- [GitHub Copilot 席次端點若變更回應結構會導致名單取得失敗] → 失敗已定義降級行為（卡片內顯示錯誤、不影響其他卡片）

## Migration Plan

無資料遷移。部署方式與既有流程相同：更新程式碼後重建容器即可。回滾方式為還原本次變更的兩個檔案修改，其餘卡片與路由不受影響。

## Open Questions

無。資料源可用性、欄位名稱與請求數策略均已以實際 API 回應驗證。
